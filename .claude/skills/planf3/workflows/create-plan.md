# Create Plan

1. Analyze Requirements - THINK HARD and parse the `USER_PROMPT` to understand the core problem and desired outcome
2. Explore Codebase - Understand existing patterns, architecture, relevant files, and prior specs to back-reference. Read `AI_DOCS` for AI/agent-facing documentation and `APP_DOCS` for application documentation to ground the plan.
3. **Verify Against Reality** - MANDATORY for any **defect / bug-fix plan** (a plan whose phases are "fix X"). A root cause read out of source code is a **HYPOTHESIS, not a finding** — static analysis is a hypothesis generator that presents as a conclusion. Before you assign a root cause to any defect, confirm it against something outside the source:
   - **Query the database.** If the theory depends on data (a stale value, an orphaned row, a null column), `SELECT` it. A theory that "column X holds a stale 0" dies instantly if column X is empty.
   - **Drive the real screen.** Reproduce the defect on a running build before planning a fix for it. If it does not reproduce, the ticket may be a stale-build retest or bad test data — say so and stop.
   - **Check the retest was valid.** Which build did the reporter test? Is the test data physically capable of passing (e.g. an `@*.test` / `.example` / `.invalid` email address can never receive mail — RFC 2606)?
   - **Confirm the surface.** Verify the screen/route the ticket describes is the one you traced. A fix landed on the wrong code path is indistinguishable from no fix at all.
   - If you cannot verify a cause empirically, **label it explicitly as a hypothesis in the plan** and make its verification the first task of that phase. Never write an unverified cause as though it were established.
4. Design Solution - Develop technical approach including architecture decisions and implementation strategy
5. Resolve Blocking Decisions - If the design surfaced any blocking decision (a choice where guessing wrong inverts the work — see the Decisions vs. Questionables rule in the Instructions), put it to the user NOW via AskUserQuestion with the options and your recommendation. Record answers as `[resolved: <choice>]`; only park a decision as `[open]` when it genuinely needs someone who isn't in the conversation, and name that owner
6. Author HTML Plan - Fill the `## Plan Template`, replacing every `{{PLACEHOLDER}}` and repeating `<!-- repeat -->` blocks as needed. The `Decisions Required` section is mandatory — populate it with every blocking decision (or "None."), each marked `[open]`/`[resolved: <choice>]` with owner and the phases it blocks. For a defect plan, every phase MUST open with a **Reproduce-or-close** task: prove the defect exists on a running build (or against real data) before any fix task — a plan that cannot prove the bug exists must not schedule work to fix it.
7. Generate Images - Run the Create sub-workflow in `workflows/image-generation.md` to fill the `{{...IMAGE` slots. Parallelize the image generation as there's no reason to block here.
8. Surface Questionables - If `QUESTIONABLE` is true, populate the conditional Questionables section with open decisions/assumptions/risks; otherwise omit the section. Any root cause that survived step 3 only as a hypothesis belongs here. Blocking decisions do NOT live here — they are already in `Decisions Required`
9. Generate Filename - Create a descriptive kebab-case filename based on the plan's main topic
10. Save - Write the plan to `PLAN_FILE` and provide a summary of key components. The summary MUST end with the decision status line: either `⚠ N unresolved decision(s) — Phase(s) X blocked until answered (owner: …)` or `No open decisions.` — never omit it
11. Open in Browser - Open the saved plan in `BROWSER` (e.g. `open -a "Google Chrome" PLAN_FILE`)
