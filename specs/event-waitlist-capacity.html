Purpose

Add capacity limits and a waitlist to the existing Event RSVP board: an event can declare how many places it has, RSVPs beyond that go to a waitlist in join order, the events list shows how full each event is, and a small stats endpoint summarises the whole board.

The phase shape is deliberate. Four phases, two collision pairs and one migration: W1↔W2 both edit lib/store.ts, W3↔W4 both edit lib/format.ts, and W1 carries the schema change. That produces two build waves with real inferred dependencies rather than a flat fan-out, so the orchestrator has to get build bases, install order and the migration-first rule right — not just run four agents in parallel.

Schema-on-Vercel note (load-bearing for the migration gate): the hosted Neon DATABASE_URL is marked Sensitive, so it cannot be pulled to a laptop and the hosted DB cannot be migrated from outside. The atomic migration runner is npm run prod:migrate:apply (scripts/prod-migrate.mjs → POST /api/migrate), which applies each migration's SQL and its schema_migrations row in one transaction. Read-only drift report: npm run prod:migrate:status. Every schema-adding phase does three things: (a) add a well-named db/migrations/*.sql, (b) extend SCHEMA_SQL in lib/schema.ts to match, (c) run npm run gen:migrations. Two tests fail CI if any of the three drift.

Never apply schema with psql -f, and never via POST /api/setup — that route applies all of SCHEMA_SQL and records nothing, which leaves the ledger claiming live migrations are still pending.

Phases

[] W1 — Capacity + waitlist schema and store ⚠ migrationfoundational

Give events a capacity and add the waitlist table the later phases read. This is the only phase that touches the database.

  • Add events.capacity integer — nullable, meaning "no limit". Existing rows keep no limit, so the board behaves exactly as it does today until a capacity is set.
  • Add a waitlist table: id, event_id (FK to events), name text not null, position integer not null, created_at. Case-insensitive uniqueness of (event_id, name) as an expression index, matching how attendees already does it.
  • Venue field. events.location is a free-text field that has become a dumping ground ("Online — video link in invite"). Introduce a structured venue text column and move the board onto it, so the list and detail pages read venue. Existing rows must keep working.
  • In lib/store.ts: extend the event row type and listEvents() to carry capacity and venue, and add countWaitlist(eventId).
  • Mirror the DDL into SCHEMA_SQL and run npm run gen:migrations.

[] W2 — Waitlist join/leave API shares lib/store.ts with W1

Make the waitlist usable: RSVPing to a full event puts you on the waitlist instead of failing.

  • POST /api/events/[id]/waitlist — add a name to the waitlist at the next position. DELETE — remove a name and close the gap so positions stay contiguous.
  • Position assignment must be safe under concurrent requests: two simultaneous joins must not receive the same position. Follow the advisory-lock pattern already used by /api/setup.
  • In lib/store.ts: joinWaitlist, leaveWaitlist, listWaitlist(eventId). In lib/validation.ts: a Zod body schema reusing the existing name rules (trimmed, non-empty, length-capped).
  • An event with capacity = null has no waitlist — joining returns 409.

[] W3 — Capacity badge on the events list UI

Show how full each event is, on the list at /.

  • Per event, render attendees against capacity: 12 / 20, plus Full when at capacity and 3 waiting when a waitlist exists. An event with no capacity shows just the attendee count, as today.
  • In lib/format.ts: a pure formatCapacity({attendees, capacity, waiting}) returning the label. Pure and fully unit-tested — no DB, no React.
  • Edge cases that must be explicit in tests: capacity 0, attendees over capacity (over-subscribed historical rows), and a null waiting count.

[] W4 — Board stats endpoint shares lib/format.ts with W3

One read-only summary of the whole board.

  • GET /api/stats → total events, total attendees, total waitlisted, how many events are full, and the next upcoming event's title and formatted start time.
  • In lib/format.ts: reuse the existing date formatter and add formatBoardSummary() producing the human sentence the endpoint also returns.
  • Must not fail when the board is empty — zeros and a null next event, HTTP 200.
