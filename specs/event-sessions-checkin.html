Purpose

Multi-session events. A conference day is one event with several sessions; an attendee picks a session, and organisers check people in at the door. The event page shows the day's schedule, and one endpoint reports attendance across the board.

The phase shape is deliberate. Four phases, two collision pairs and one migration: X1↔X2 both edit lib/store.ts, X3↔X4 both edit lib/format.ts, and X1 carries the schema change. That produces two build waves with real inferred dependencies rather than a flat fan-out, so the orchestrator has to get build bases, install order and the migration-first rule right — not just run four agents in parallel.

Schema-on-Vercel note (load-bearing for the migration gate): the hosted Neon DATABASE_URL is marked Sensitive, so it cannot be pulled to a laptop and the hosted DB cannot be migrated from outside. The atomic migration runner is npm run prod:migrate:apply (scripts/prod-migrate.mjs → POST /api/migrate), which applies each migration's SQL and its schema_migrations row in one transaction. Read-only drift report: npm run prod:migrate:status. Every schema-adding phase does three things: (a) add a well-named db/migrations/*.sql, (b) extend SCHEMA_SQL in lib/schema.ts to match, (c) run npm run gen:migrations. Two tests fail CI if any of the three drift. Do not reuse a version prefix — the next free one is 20260727010000.

Never apply schema with psql -f, and never via POST /api/setup — that route applies all of SCHEMA_SQL and records nothing, which leaves the ledger claiming live migrations are still pending.

Deploy ordering constraint specific to this sandbox: because the runner lives inside the deployed app, a migration can only be applied after the code carrying it is deployed. That is the reverse of a laptop-run migrator. It does not relax the expand/contract rule — it tightens it: a migration here is always applied while an older build is still serving traffic, so it must be safe against both schemas.

Phases

[] X1 — Sessions schema and store ⚠ migrationfoundational

Introduce sessions and the check-in field the later phases read. This is the only phase that touches the database.

  • Add a sessions table: id, event_id (FK to events), title text not null, starts_at timestamptz not null, room text, created_at. A session belongs to exactly one event. Titles are unique per event, case-insensitively, as an expression index — matching how attendees and waitlist already do it.
  • Attendance is per session now. An attendee attends a specific session, so attendees needs a session_id pointing at it (FK to sessions). AMENDED (G0): this column is NULLABLE and stays nullable in this migration. The product intent — "an attendee with no session is meaningless" — is real, but a database-enforced NOT NULL here is not expand-safe and would break the build still serving traffic: the deployed RSVP path inserts only (event_id, name) (lib/store.ts), so every old-build RSVP would start failing the moment the migration commits — and in this repo the migration is guaranteed to be applied while the previous build is live, because the runner lives inside the deployed app. The NOT NULL is deferred to a later CONTRACT migration, once no deployed build writes session-less attendees. Enforce the requirement in application code now (X2 writes session_id on every new RSVP).
  • Backfill, so X4 does not undercount. Existing attendees predate sessions. Create one legacy session per event that already has attendees (title "General Admission", starts_at = the event's starts_at, null room) and point those attendees at it, so historical attendance is attributed rather than invisible. This is a scoped UPDATE … WHERE session_id is null, not a blanket rewrite — the static screen reports it as a note, and that note is expected and accounted for here.
  • Check-in. Add attendees.checked_in_at timestamptz, null meaning "not yet arrived".
  • Naming cleanup. attendees.created_at is misleading — it is the moment someone RSVPed, not a row-creation timestamp, and two reports have already been written against the wrong reading. Introduce the accurate name rsvped_at. AMENDED (G0): this is an ADD + backfill, NOT a RENAME. A RENAME COLUMN breaks the live build's attendee query, which selects and orders by created_at (lib/store.ts), and the static safety screen rejects RENAME outright. Add rsvped_at timestamptz, backfill it from created_at, default it for new rows, and keep created_at in place. Retiring created_at is a later CONTRACT migration.
  • In lib/store.ts: extend the attendee type with sessionId and checkedInAt, and add listSessions(eventId). AMENDED (G0): listSessions returns each session with its attendeeCount and checkedInCount, ordered by starts_at then title (the stable tiebreak X3's tests assert). X3 renders exactly these numbers, so they belong to this phase's single aggregate query — if X3 added its own store method instead it would collide with this phase on lib/store.ts. Read rsvped_at via coalesce(rsvped_at, created_at) so the store is correct against both schemas.
  • Seed a multi-session event — through the migration, not /api/setup. SEED_EVENTS seeds events only, so no session rows can exist and X3's "seeded multi-session event" exit condition is unreachable. AMENDED (G0 round 2): the fixture must arrive via the recorded migration. POST /api/setup is a hard stop in this run (it applies all of SCHEMA_SQL and records nothing), so a seed that only lives there can never legitimately reach the hosted database. Therefore the migration itself seeds the demo sessions idempotently and scoped (insert … where not exists / on conflict do nothing, keyed on event + title) — it arrives through npm run prod:migrate:apply like the rest of the migration. Seed two sessions at the same starts_at on one event (exercises the title tiebreak) and leave one event with zero sessions (X3 must prove that page is unchanged). Also add SeedSession data to lib/schema.ts and teach app/api/setup/route.ts to seed sessions inside its existing advisory-locked transaction, so the fresh-bootstrap path stays coherent — that route is not used by this run, but leaving it events-only would make a from-scratch database disagree with a migrated one.
  • Plumb sessions into the page and the RSVP form — in THIS phase. AMENDED (G0 round 2): this is what keeps X2 and X3 parallel. RsvpForm is a client component that today receives only eventId, and app/events/[id]/page.tsx passes only that. A session picker therefore needs the server page to call listSessions and pass serializable sessions down — and if X2 did that, X2 and X3 would both edit page.tsx in the same wave. So X1 does the plumbing: the page calls listSessions(event.id) and passes a sessions prop into RsvpForm, which accepts it (typed, optional, rendering nothing new yet). X2 then only fills in the picker UI inside rsvp-form.tsx, and X3 only renders the schedule in page.tsx. No same-wave collision. listSessions must degrade gracefully if the sessions table does not exist yet (use the existing isUndefinedTable helper) — the code deploys before the migration is applied.
  • Mirror the DDL into SCHEMA_SQL and run npm run gen:migrations. AMENDED (G0): tests/unit/schema-drift.test.ts pins the migration filename list to the current three files and will fail the moment a fourth is added — update that list in this phase, or npm test cannot go green.

[] X2 — Check-in API shares lib/store.ts with X1

Let an organiser mark an attendee as arrived, and undo it.

  • POST /api/events/[id]/checkin — body names the attendee and the session; sets checked_in_at to now. Idempotent: checking in twice does not move the timestamp and returns 200, not 409.
  • DELETE — clears checked_in_at (someone scanned the wrong badge).
  • Checking in against a session that does not belong to that event is a 404, not a 500.
  • In lib/store.ts: checkIn, undoCheckIn, countCheckedIn(sessionId). In lib/validation.ts: a Zod body schema reusing the existing name rules (trimmed, non-empty, length-capped).
  • AMENDED (G0): make RSVP session-aware — nothing else does. X1 leaves session_id nullable on purpose, so unless a write path sets it, every new attendee is session-less forever: they cannot be checked in, and X4 undercounts. This phase owns that path because it already owns lib/validation.ts. Extend rsvpInput with a sessionId, have the RSVP route and store write it, and 404 if the session does not belong to that event — the same rule as check-in. Note rsvpInput is .strict(), so an unknown key is already a 400: the picker in the form below and this schema change must land in the same phase or the form's POST is rejected.
  • AMENDED (G0 round 2): sessionId is CONDITIONALLY REQUIRED, not merely optional. A plain optional field would let a caller omit it and silently recreate the session-less attendee this plan exists to eliminate — X4 would undercount again. The rule: if the event has one or more sessions, sessionId is required and its absence is a 400; omission is accepted only when the event has no sessions (which is what keeps the zero-session form working unchanged). Both branches are unit-testable with a mocked query and both must be tested.
  • Add a session picker to the RSVP form (app/events/[id]/rsvp-form.tsx) when the event has sessions, so the feature is reachable from the UI and not merely from curl. An event with no sessions keeps its current single-field form exactly as it is. X1 already passes the sessions prop in, so this phase does not touch app/events/[id]/page.tsx — that file belongs to X3, and touching it here would collide inside wave 2.
  • Use the existing advisory-lock pattern rather than a read-then-write if any sequence number is assigned; idempotency and the 404s are concurrency requirements, and all of them are testable at unit level with a mocked query.

[] X4 — Attendance report endpoint shares lib/format.ts with X3

One read-only view of who actually turned up.

  • GET /api/attendance → per event: session count, attendee count, checked-in count and a show-up rate; plus board totals and the busiest session.
  • In lib/format.ts: add formatShowUpRate() producing the human string the endpoint also returns. Zero attendees must not divide by zero — report "no attendees yet", not NaN.
  • Must not fail when the board is empty — zeros, a null busiest session, HTTP 200.
  • AMENDED (G0): pin the contract, or the output is nondeterministic and untestable. Fix all of the following explicitly:
    • Response shape: { events: [{ id, title, sessionCount, attendeeCount, checkedInCount, showUpRate, showUpRateLabel }], totals: { events, sessions, attendees, checkedIn, showUpRate, showUpRateLabel }, busiestSession: { id, eventId, title, attendeeCount } | null }.
    • Event ordering: newest first, matching listEvents().
    • Rate format: showUpRate is a number rounded to one decimal place (percent, 0–100); showUpRateLabel is formatShowUpRate()'s human string, and is "no attendees yet" when the denominator is zero. Never NaN or Infinity.
    • Busiest-session tiebreak: highest attendeeCount, then earliest starts_at, then lowest id. Null only when there are no sessions at all.
