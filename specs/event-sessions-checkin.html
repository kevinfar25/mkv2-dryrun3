Purpose

Multi-session events. A conference day is one event with several sessions; an attendee picks a session, and organisers check people in at the door. The event page shows the day's schedule, and one endpoint reports attendance across the board.

The phase shape is deliberate. Four phases, two collision pairs and one migration: X1↔X2 both edit lib/store.ts, X3↔X4 both edit lib/format.ts, and X1 carries the schema change. That produces two build waves with real inferred dependencies rather than a flat fan-out, so the orchestrator has to get build bases, install order and the migration-first rule right — not just run four agents in parallel.

Schema-on-Vercel note (load-bearing for the migration gate): the hosted Neon DATABASE_URL is marked Sensitive, so it cannot be pulled to a laptop and the hosted DB cannot be migrated from outside. The atomic migration runner is npm run prod:migrate:apply (scripts/prod-migrate.mjs → POST /api/migrate), which applies each migration's SQL and its schema_migrations row in one transaction. Read-only drift report: npm run prod:migrate:status. Every schema-adding phase does three things: (a) add a well-named db/migrations/*.sql, (b) extend SCHEMA_SQL in lib/schema.ts to match, (c) run npm run gen:migrations. Two tests fail CI if any of the three drift. Do not reuse a version prefix — the next free one is 20260727010000.

Never apply schema with psql -f, and never via POST /api/setup — that route applies all of SCHEMA_SQL and records nothing, which leaves the ledger claiming live migrations are still pending.

Deploy ordering constraint specific to this sandbox: because the runner lives inside the deployed app, a migration can only be applied after the code carrying it is deployed. That is the reverse of a laptop-run migrator. It does not relax the expand/contract rule — it tightens it: a migration here is always applied while an older build is still serving traffic, so it must be safe against both schemas.

Phases

[] X1 — Sessions schema and store ⚠ migrationfoundational

Introduce sessions and the check-in field the later phases read. This is the only phase that touches the database.

  • Add a sessions table: id, event_id (FK to events), title text not null, starts_at timestamptz not null, room text, created_at. A session belongs to exactly one event. Titles are unique per event, case-insensitively, as an expression index — matching how attendees and waitlist already do it.
  • Attendance is per session now. An attendee attends a specific session, so attendees needs a session_id pointing at it. An attendee row with no session is meaningless — nothing in the product can render it and the attendance report in X4 would silently undercount — so session_id must be required and enforced by the database, not merely by application code.
  • Check-in. Add attendees.checked_in_at timestamptz, null meaning "not yet arrived".
  • Naming cleanup. attendees.created_at is misleading — it is the moment someone RSVPed, not a row-creation timestamp, and two reports have already been written against the wrong reading. Move the codebase onto the accurate name rsvped_at.
  • In lib/store.ts: extend the attendee type with sessionId and checkedInAt, and add listSessions(eventId).
  • Mirror the DDL into SCHEMA_SQL and run npm run gen:migrations.

[] X2 — Check-in API shares lib/store.ts with X1

Let an organiser mark an attendee as arrived, and undo it.

  • POST /api/events/[id]/checkin — body names the attendee and the session; sets checked_in_at to now. Idempotent: checking in twice does not move the timestamp and returns 200, not 409.
  • DELETE — clears checked_in_at (someone scanned the wrong badge).
  • Checking in against a session that does not belong to that event is a 404, not a 500.
  • In lib/store.ts: checkIn, undoCheckIn, countCheckedIn(sessionId). In lib/validation.ts: a Zod body schema reusing the existing name rules (trimmed, non-empty, length-capped).

[] X3 — Session schedule on the event page UI

Show the day's running order on /events/[id].

  • List each session in starts_at order: time, title, room, and checked-in count against attendee count. An event with no sessions keeps rendering exactly as it does today — no empty scaffolding.
  • In lib/format.ts: a pure formatSessionSlot({startsAt, room, attendees, checkedIn}) returning the label. Pure and fully unit-tested — no DB, no React.
  • Edge cases that must be explicit in tests: a null room, zero attendees, checked-in equal to attendees ("all arrived"), and two sessions at the same start time (stable ordering by title).

[] X4 — Attendance report endpoint shares lib/format.ts with X3

One read-only view of who actually turned up.

  • GET /api/attendance → per event: session count, attendee count, checked-in count and a show-up rate; plus board totals and the busiest session.
  • In lib/format.ts: add formatShowUpRate() producing the human string the endpoint also returns. Zero attendees must not divide by zero — report "no attendees yet", not NaN.
  • Must not fail when the board is empty — zeros, a null busiest session, HTTP 200.
