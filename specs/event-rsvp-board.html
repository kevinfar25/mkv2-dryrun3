Purpose

Grow the baseline Next.js app from a placeholder landing page + /api/health into a small but complete Event RSVP board: list events, create an event, view an event and RSVP to it with a live attendee count, and drill into an event's attendee list. The work is split into six phases with deliberately shaped file overlaps so a parallel-build orchestrator (Magic Kingdom V2) has a real dependency graph to reason about — some phases are independent, some share lib/store.ts, lib/schema.ts, app/layout.tsx, or the event-detail page, and two carry migrations. Every read/write flow is exercised through a real browser (Playwright) on the deployed Vercel app, not curl.

Schema-on-Vercel note (load-bearing for the functional gates): the hosted Neon DATABASE_URL is marked Sensitive, so it cannot be pulled to a laptop and the DB cannot be migrated from outside. Schema is applied to the hosted DB by a token-guarded POST /api/setup (built in P1) that runs the canonical DDL held in lib/schema.ts (SCHEMA_SQL) + a seed, from inside the deployed function. Every schema-adding phase therefore does BOTH: (a) add a well-named db/migrations/*.sql file (satisfies the migration-hygiene CI check + the migration safety gate's static screen) AND (b) extend SCHEMA_SQL to match — kept byte-for-byte equivalent and expand-only. The two must not diverge.

Phases

[] P1 — Events foundation + setup route ⚠ migrationM1foundational

Introduce the events table, the persistence seam over lib/db.ts, the Zod input schema, and the token-guarded setup route that seeds the hosted DB. Every later phase depends on this.

  • Add migration db/migrations/20260725010000_events.sql creating events(id serial pk, title text not null, starts_at timestamptz not null, location text not null, created_at timestamptz not null default now()).
  • Add lib/schema.ts exporting SCHEMA_SQL (the SAME DDL as the migration, idempotent CREATE TABLE IF NOT EXISTS …) and a small SEED_EVENTS array. Keep SCHEMA_SQL and the migration equivalent + expand-only.
  • Add lib/store.ts over query() from lib/db.ts: createEvent({title, startsAt, location}), listEvents() (newest first), getEvent(id) (or null). No ORM — parameterized SQL.
  • Add lib/validation.ts: a Zod eventInput schema (title non-empty ≤120 chars, startsAt ISO datetime, location non-empty ≤160 chars) with a parseEventInput(raw) returning a typed result.
  • Add app/api/setup/route.ts: POST, force-dynamic, guarded by header x-setup-token === process.env.SETUP_TOKEN (401 otherwise; 500 if unset). Applies SCHEMA_SQL; if body {"seed":true}, inserts SEED_EVENTS (idempotent — ON CONFLICT DO NOTHING or guard by count). Returns { ok, schema:"applied", seeded }.
  • Unit-test lib/validation.ts in lib/validation.test.ts (hermetic — no DB): valid input parses; each invalid field (empty title, bad datetime, over-length) is rejected. CI has NO database — never unit-test the store/DB directly.
